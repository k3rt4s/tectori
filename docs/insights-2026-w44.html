A Shared ChatGPT Link Could Run Attacker Code in Your Session and Read Private Chats

A shared ChatGPT link could allow attackers to run code in a victim's session and read private chats due to a vulnerability in untrusted HTML execution.

A shared ChatGPT link could run attacker code in the victim's session and read private chats. The flaw was reported through OpenAI's bug bounty and fixed within eight days. The attack relied on a public link containing HTML and an interactive graph that loaded a math library. This allowed the attacker to bypass the sandbox and inject code into the main ChatGpt page.

The code executed with the victim's full web access, enabling the attacker to read private conversations and perform actions on their behalf. The vulnerability stemmed from three design choices that allowed untrusted HTML to bypass security boundaries. OpenAI addressed the issue by blocking the messages the attack relied on.

This highlights the risks of untrusted HTML execution in LLM interfaces. Sandboxing and input validation are critical to prevent code from running in the main application. Developers must ensure all external content is properly sanitized and that cross-frame communication is strictly controlled.

For users, there's no action needed. OpenAI has fixed the issue on their end. But for teams building AI systems, this serves as a reminder to prioritize security in every layer of the stack. Input validation and sandboxing are non-negotiable.

Hackers could poison AI models by tampering with core infrastructure

Hackers can compromise AI models by tampering with underlying infrastructure components like firmware and software.

Hackers can sabotage AI models by tampering with their underlying infrastructure like firmware and software. This isn't just a theoretical risk. Eclypsium's report shows how subtle changes in runtime can bias models toward insecure behaviors. It's a critical issue that demands attention from AI labs and businesses using these systems.

The runtime state of an AI model is controlled by a complex hierarchy of software, firmware, and hardware. Each layer represents a potential entry point for attackers. The host machine is the easiest target, relying on OS, kernel, and drivers. These are vulnerable to malware like rootkits that persist below the OS level.

Third-party components like firmware update services and management controllers also create risks. Compromising the management plane can allow firmware changes or direct control of devices. DPUs, used by chipmakers, are especially sensitive. They can be exploited to alter a model's operating state without changing the model file itself.

Eclypsium recommends securing DPUs independently and maintaining accurate inventories of all components. Trusted AI requires visibility into every part of the infrastructure stack. We need to verify components, not just assume the model boundary starts at the container.
